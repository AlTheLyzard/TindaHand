# Owner Profile and Operator management

Implemented the Owner frontend for MA-PRO-001–003 and the account-management part of MA-PRO-002. No backend endpoints, transport schemas or live profile integrations existed in the inspected project. The replaceable adapters remain explicit opt-in development mocks. No dependencies, database migrations or native build configuration were added.

Sources actually reviewed: root AGENTS.md; the workbook's named MAY-ARI MODULE (MA-PRO-001–003, MA-LOG-004, MA-SET-001) and KAHERA MODULE access/login criteria; relevant comparison rows in Copy of MAY-ARI MODULE; Requirements Engineering and relevant Project Charter sections; frontend plan, current authentication handoff, Settings, Menu, button/motion, API and backend notes. The baseline and copy sheets agree on the profile/access-control rows. They differ on initial Operator setup wording, confirmation fields and Add Another behavior; the original documents are unchanged. Older setup criteria expose an Operator PIN, and the reference's reactivation dialog wrongly describes losing access. The current user instruction governs: multiple Operators, no displayed/retrieved previous PIN, corrected restored-access copy and English Owner/Operator labels. Owner ID is immutable. The original Android-only scope remains superseded by AGENTS.md's Android-and-iOS decision.

Routes and behavior:

- `/owner-menu/profile`: overview, immutable Owner ID, optional store fallback “Not set”, registered email, pending-email notice, Manage Operators, existing Settings and confirmed full logout. The legacy header/drawer profile entry redirects here. Shared name/avatar displays update from the same profile snapshot.
- `/owner-menu/profile/edit`: separate draft. Avatar selection and current-PIN verification are full-screen stages within this route, so no credentials enter route params. The avatar stage has an isolated preview and explicit Apply/Cancel. Save validates, asks “Save Changes?”, verifies the current four-digit masked Owner PIN, then commits through the service. Validation updates after interaction. Failed saves preserve the draft; each verification attempt clears the PIN input. Back/Cancel/Android back and native stack removal are guarded; header navigation also requests discard when dirty. Keep Editing retains the draft. SDK 58's `usePreventRemove` handles native stack removal and web unload confirmation.
- `/owner-menu/profile/email`: pending, failed/expired, check, resend, cancel and successful-verification states. Saving other fields may succeed while the email stays pending. The registered address remains active for recovery until verified. The development flow explicitly says no email was sent; “Simulate Verified Email (Development)” exists only for the enabled mock. There is no real delivery/link integration. Server-side cooldown and 15-minute expiry are modeled by the mock, not an established production policy.
- `/owner-menu/profile/operators`: shared list/empty state and Add Operator. Settings → User Management redirects to this exact feature. Stable internal IDs target management actions.
- `/owner-menu/profile/operators/new`: reuses `CredentialForm`, the same account-setup form used during registration. The Owner creates the Operator and assigns/confirm its PIN. Success opens account details; Back reaches the updated list.
- `/owner-menu/profile/operators/[operatorId]`: account identity/status, linked Owner ID, four immediate permission switches, compact saving/saved feedback, optimistic rollback/retry, reset action and confirmed deactivate/reactivate. Requests are serialized; each Operator has independent stored permissions. Inactive switches are disabled and visually off without erasing capabilities. Status changes never delete historical records or attribution.
- `/owner-menu/profile/operators/reset-pin`: reuses masked PIN setup/validation with current Owner reauthentication, new PIN and confirmation. No previous Operator PIN is retrieved. Existing Settings PIN-reset entry remains supported and now calls the same authenticated mutation wrapper.

Profile and child screens use the shared safe-area/background, keyboard avoidance and scrolling, with no bottom navigation. Actions remain in scroll content so they can be reached on smaller screens/larger text. Avatar cells expose labels/selected state; switches expose checked/disabled state with 48-point touch targets. Existing motion honors reduced motion. Confirmation dialogs use the shared modal and explicitly focus Close.

Proposed integration seams (not HTTP endpoints):

| Adapter | Proposed request → response |
| --- | --- |
| `AuthenticationService.profile.read` | authenticated session context → canonical `OwnerProfile` |
| `profile.save` | editable `ProfileDraft` + request-only current Owner PIN → canonical profile with immutable Owner ID and optional `PendingEmail`; registered email unchanged until verified |
| `profile.email` | check/resend/cancel intent; production verified-link callback must replace the development simulation → canonical profile/pending status |
| `createOperator` | name + assigned PIN; confirmation stays UI-only → credential-free canonical Operator identity/status |

| `setOperatorPermission` | internal Operator ID + one fixed permission group + allowed boolean → canonical capabilities |
| `setOperatorActive` | internal Operator ID + active boolean → canonical Operator status |

`src/types/profile.ts` defines proposed frontend profile contracts, `src/data/profile.ts` supplies fictional demo values, `src/services/profile.ts` implements the in-memory lifecycle, and `src/utils/profile*.ts` separates validation/draft behavior. Authentication owns the adapter's actor context and synchronizes confirmed identity/email with its recovery lookup. No UI Owner/store ID grants authorization. Account mutations recheck the originating live session after their asynchronous boundary. PINs are transient request inputs or isolated mock credential closures, never profile records, persisted drafts, route params or logs.

Backend TODOs identify server validation/immutable Owner ID, current-owner reauthentication and throttling, canonical responses, email delivery and single-use verification links, atomic uniqueness checks, store ownership, capabilities, credential hashing, active-session invalidation and audit attribution. Production must enforce permissions on every request; client route checks are not security. Future persistence should normalize accounts, stores, operator memberships and permissions, referencing Owner/store identities without duplicating their details. No database schema or migration is proposed here.

Operator login preserves the agreed **Owner ID + assigned four-digit Operator PIN** contract. Existing mock rules require distinct PINs among active Operators in the same store; no new login identifier was introduced. Reactivation refuses a conflicting PIN until reset. Backend atomicity, rate limits and the limited four-digit credential space still require an approved security contract. Permission changes, PIN resets and status changes invalidate the affected mock Operator session. Only the fixed operational capabilities can be assigned; financial statements, store debts, expenses, access control, product creation/deletion and asset writes stay Owner-only.

Operator login now opens the shared POS workspace with the three-item navigation. Inventory and More remain guarded placeholders. This phase does not expose Owner routes or actions to Operators; `hasCapability` centralizes the operational allowlist and continues to gate this Owner administration stack. Saved permissions are used by mock Operator login, and the POS route checks its capability directly. Additional Operator features remain for later phases.

## Unique avatars within each store (November 11, 2026)

The shared in-memory service in `src/services/avatars.ts` now owns store-scoped avatar assignments for both the profile and Operator-creation adapters. The current mock model uses the linked Owner ID as the store key. New Operators receive the first free ID in the existing shared picker order; the Owner and every Operator, including inactive accounts, reserve their selections. Different stores can reuse presets. With 12 supplied assets, a store supports one Owner and at most 11 Operators. Exhaustion prevents creation without consuming an account ID, storing a PIN or publishing a partial record, and explicitly reports that additional avatar assets are needed.

Explicit mock hydration applies a pure migration plan: retain a valid Owner selection, preserve valid Operator selections in code-point Operator ID order, then fill missing/invalid/duplicate assignments in that same stable order. Preserving valid selections happens before gap filling so that an earlier missing account cannot steal a later valid selection. If the Owner has no valid selection, they receive the first unreserved preset. More than 12 existing accounts cannot be reconciled with these assets; the service returns the exhaustion error without publishing partial assignments. Migration is a service-initialization operation, never a write triggered by screen rendering, reading a profile or opening the editor. Repeated initialization preserves saved assignments.

The picker keeps the current account's avatar selectable. Other accounts' presets show “In use” and expose disabled semantics to assistive technology. Apply and the final profile save recheck availability. A conflict at save returns to the picker with the full draft intact and asks for another selection. The old reservation is released only after successful save; cancellation, validation/PIN/email failures and simulated service failures leave assignments unchanged. Operator list/details, Settings PIN-management identities and shared navigation portraits use the assigned preset rather than a fixed per-ID lookup. The shared portrait primitive preserves the circular crop and blue background; picker entrance/selection animations and reduced-motion handling remain in place.

Backend integration remains deferred. `BACKEND TODO` comments call for transactional account creation/avatar replacement, a store-wide uniqueness constraint covering both roles and inactive accounts, and migration of legacy missing/duplicate values. These frontend checks coordinate one mock instance only and cannot prevent simultaneous assignment conflicts between devices. The relevant named workbook role sheets were reread; this refinement follows the current user instruction, while the previously documented setup/copy-sheet conflicts remain unchanged.
