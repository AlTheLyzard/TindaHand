# Accounts Payable — MA-AP-001–004

Frontend-only implementation using the four `docs/designs/MA-AP-00*.png` exports. There is no root `designs/` directory or AP `(1)` variant in this checkout. The named MAY-ARI MODULE sheet in the original requirements workbook is the baseline; source requirements remain unchanged.

Account Balances lives at `/owner-menu/receivables-payables`. Receivable retains the existing customer-debt list and Customer Debt Quick Add. This task does not implement MA-AR-001–004, which previously had only a session-record placeholder. Payable has Unpaid/Paid tabs, creditor search, expandable debt details/history, creation, creditor selection and payment entry. All nested routes inherit the owner gate; cashier login does not grant an owner identity.

The blue unpaid summary includes every outstanding debt regardless of search and counts distinct creditor IDs. Pending means no confirmed payments; Remaining Balance means partial payment with a positive balance. Cards prominently show the remaining balance. Paid records have zero balance; their green summary includes only fully settled debts matching the search, at original settled value. Progress uses cumulative confirmed payments divided by original debt. Search always follows the Unpaid/Paid tabs. The screenshot's conflicting search positions, labels, totals, percentages and partial-preview status follow the user's confirmed corrections.

New Business Debt accepts a typed or selected creditor, positive exact-centavo amount, optional clearable due date and notes. Validation appears on submission and updates with corrections. The form remains mounted beneath the creditor route, with its draft above both routes. Save tokens and synchronous tap guards prevent duplicate saves. Cancel/back creates no record. The existing Quick Add Store Debt default date policy is preserved; the full form starts with no due date.

`createQuickAddService` delegates Store Debt to `createPayablesRepository`. `useQuickAdd` exposes the same ledger to both entry points; its combined records adapt payables to the existing remaining-balance convention. Other Quick Add variants and POS customer debts keep their existing behavior. Payable creditors, debts and payment events have stable IDs, integer-centavo amounts, date-only due dates and ISO event timestamps. Seeds are cloned into editable repository state, filtered by owner, and are never mutated. Selected IDs are validated; typed names reuse normalized existing identities as a demo convention (same-name real suppliers require a backend identity policy).

Payment typing and shortcuts only change a local preview. Full Payment replaces the field with the exact outstanding amount; +₱500/+₱1,000/+₱2,000 add repeatedly and disable when they would exceed the balance. Confirmation revalidates against current repository history, appends one event and updates all derived views. Full settlement returns to Paid; partial payment returns to Unpaid. Expanded cards expose payment amounts and Manila dates/times, including the final paid date.

The repository is a replaceable in-memory boundary. No backend requests, persistence, inventory changes, expenses, cash movements, interest or allocation rules are introduced. Records survive navigation and retain the existing provider's owner-filtered session lifetime; app reload resets them. Future integration needs server authorization, atomic writes, durable idempotency and canonical records before success feedback.

Requirements gaps: MA-AP-004 mentions a GCash reference when applicable, but the updated AP form has no payment method/reference fields and no AP schema defines them. Payments therefore record amount and timestamp only; no method is inferred. The copy owner sheet adds overview search/payment-history remarks, replaces validation with a cancellation remark, and still marks MA-AP-003/004 “To be designed.” These differences are not merged into the baseline; updated supplied designs and the explicit task decisions govern this implementation.
